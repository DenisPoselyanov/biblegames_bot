# Що треба доробити, щоб прототип став справжньою студією

Список виведений із самого прототипу: кожен екран вимагає чогось, чого зараз
немає. Номери в дужках — пункти Phase 4 майстер-специфікації, які закриває
завдання.

Порядок не випадковий: WS1–WS3 — фундамент, без якого решта екранів показує
вигадані дані; WS4–WS6 дають студії сенс; WS7–WS9 закривають acceptance criteria.

---

## WS1 · Provider layer і job runner

Без цього екрани `jobs`, `jobs/new`, `jobs/:id` малюють неіснуючу сутність.

1. Єдиний контракт провайдера для Ollama / Gemini / OmniRoute / MockProvider:
   `generateText` · `generateObject` · `generateArray`, кожен повертає provider,
   model, attempt, duration, usage, warnings. *(AI provider layer)*
2. Provider-specific env замість спільного `AI_MODEL`: `GEMINI_MODEL`,
   `OLLAMA_MODEL`, `OMNIROUTE_MODEL`. Модель не змінюється непомітно.
3. Таблиця `ai_jobs`: id, task, requester, provider/model, input hash, status,
   attempts, retry policy, budget, checkpoint, retention, result ref. *(Job runner)*
4. Виконавець із чергою: `queued → running → completed | partial | failed |
   cancelled`, checkpoint після кожної партії, resume з checkpoint, cancel.
5. Бюджети як жорсткі зупинки: запити, токени, вартість. Досягнення ліміту —
   зупинка зі збереженим checkpoint, а не мовчазне продовження.
6. Журнал джоба як окремий потік подій, із рівнями info/warn/error.
7. MockProvider покриває orchestration-тести. *(acceptance: без нього CI не проходить)*

**Готово, коли:** джоб можна запустити, скасувати, продовжити й переглянути
журнал; бюджет зупиняє роботу; повтор із тим самим хешем входу не створює
дубль-сутності.

## WS2 · Модель контенту: чернетки, ревізії, статуси

Без цього немає ні черги, ні diff, ні відкату.

1. Таблиці `content_drafts` і `content_revisions`: кожна published-позиція має
   ревізію й статус. *(acceptance: усі published questions мають revision і status)*
2. Життєвий цикл `draft → generated → validation_failed | ready_for_review →
   changes_requested | approved → scheduled | published → superseded | archived`
   як єдиний перехідний автомат, а не набір булевих полів.
3. Заборона запису AI у published store на рівні прав БД, не домовленості.
   *(acceptance: AI не може писати в published store)*
4. `correctIndex` без fallback: відсутнє поле — це помилка валідації, а не 0.
   *(acceptance)*
5. Field-level diff між ревізіями — те, що малює `review/:id`.

## WS3 · Валідація як конвеєр гейтів

1. Schema validation (Zod) на вході в staging.
2. Детерміновані чеки: дублікати (embeddings + поріг), мова, довжина,
   розподіл складності, зміщення до першої відповіді.
3. AI-чеки окремим класом і з іншим статусом у UI: підказка, не гейт.
4. Людські чеки (богословська чутливість) як явний пункт, який не можна
   закрити машиною.
5. Результат кожного чека зберігається з чернеткою: label, severity, detail,
   kind — рівно те, що показує права колонка картки ревʼю.

## WS4 · Перевірка Писання

1. Нормалізація посилань: «Ів 3:16», «Івана 3:16», «JHN.3.16» → один ключ.
2. Адаптер довіреного джерела (переклад Огієнка локально; далі — інші).
3. Вердикти `match | paraphrase | mismatch | not_found` і зберігання evidence:
   текст джерела на момент перевірки. *(acceptance: Scripture checks зберігають evidence)*
4. Блокування публікації для `mismatch` і `not_found`.
5. Людське рішення для `paraphrase` — зняти лапки або підтягнути дослівний текст.

## WS5 · RBAC і доступ до студії

1. Ролі `author · reviewer · admin` і права `job.run`, `job.cancel`,
   `draft.edit`, `draft.repair`, `review.comment`, `review.approve`,
   `content.publish`, `content.rollback`, `settings.write`.
2. Кожен endpoint студії fail-closed: без права — 403, навіть якщо UI сховав
   кнопку. Feature flag не замінює авторизацію.
3. Студія не входить у користувацький bundle: окремий вхід і окремий чанк.
   *(Content Studio: «не входить у звичайний user bundle»)*
4. Прив'язка середовища до сесії: публікація в production не робиться зі
   staging-сесії.

## WS6 · Публікація, релізи, відкат

1. Реліз як незмінний набір ревізій із версією, автором і нотаткою.
2. Заплановані релізи: стартують, лише якщо всі позиції `approved`.
3. Відкат повертає попередні ревізії без ручного редагування JSON.
   *(acceptance: можна rollback publication)*
4. Публікація й відкат — окремі permissioned-операції з записом в аудит.

## WS7 · Аудит

1. Журнал `audit_log`: час, актор, роль, дія, обʼєкт, деталі, evidence.
2. Пишуться й відмови (спроба без права), і системні дії (`system` = runner і
   валідатори).
3. Журнал доповнюється, не редагується; експорт за період.
   *(acceptance: є review і publication audit trail)*

## WS8 · Аналітика якості

1. Події гри: старт, відповідь, скарга — без зайвих персональних даних.
2. Агрегати: правильність питання, розподіл за смугами, зміщення до варіанта A,
   питання-викиди, скарги.
3. Зворотний зв'язок у конвеєр: «викид» одним кліком стає джобом ремонту.

## WS9 · Уніфікований CLI і прибирання legacy

1. `npm run ai -- <task> [options]` як єдиний вхід; студія і CLI ділять один
   runner. *(Unified CLI)*
2. Матриця legacy-команд: кожен старий скрипт має deprecation message,
   заміну, дату видалення, contract-тести й порівняння на golden dataset.
   *(acceptance: legacy command matrix має replacement)*
3. Повний аудит наявного банку питань за списком зі специфікації (схема,
   неправильна відповідь, дублікати, двозначність, мова, складність,
   посилання, богословська чутливість, first-option bias, сироти, порожні пули,
   зламані пояснення).
4. Вивід із експлуатації `scripts/ai_launcher.py` після того, як студія закриє
   всі його вкладки.

## Що лишилося зробити в самому прототипі

- Онбординг ролі: як виглядає студія для людини, яка зайшла вперше (екран
  «Як це працює» є, але він пасивний — його ніхто не показує сам).
- Стани завантаження й помилок мережі (зараз показані лише порожні стани).
- Екран порівняння двох довільних ревізій між собою, а не лише з опублікованою.
- Масові операції (виділити N позицій → ремонт/схвалення) — свідомо не робилися.
- Клавіатура: рух по черзі стрілками, `A` — схвалити, `R` — повернути.
- Світлу тему перевірено на око, але не проганяли через контрастний аудит
  (WCAG AA) — перед реалізацією варто прогнати, як це робили у WS10 §17.
