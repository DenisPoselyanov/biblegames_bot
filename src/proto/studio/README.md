# Прототип AI-студії (`/proto/studio`)

Клікабельний прототип **Content Studio** — захищеної поверхні з Phase 4
майстер-специфікації. Живе всередині дизайн-прототипу `proto/design-v2`,
**не змінює жодного наявного екрана** й нічого не пише в реальні дані.

## Як відкрити

```bash
npm run dev
```

далі `http://localhost:5173/proto/studio` (порт залежить від конфігурації
dev-сервера). Потрібен екран **від 1100px** — вужче студія показує чесну
заглушку замість стиснутої таблиці.

## Рішення, зафіксовані на старті

| Питання | Рішення |
|---|---|
| Що прототипуємо | єдиний Content Studio (Phase 4), а не редизайн `/admin` чи вебверсію лаунчера |
| Форм-фактор | десктоп, окремий маршрут `/proto/studio`, без телефонної рамки |
| Ролі | мультиролі з RBAC: автор · рецензент · адміністратор, перемикач у шапці |
| Обсяг | 13 екранів, включно з порожніми станами й заблокованими діями |
| Візуальна мова | та сама, що в `/proto`, але щільніша (див. нижче) |
| Копайлот | місце зарезервовано й описано, сам асистент не реалізується |
| Дані | синтетичні, підібрані так, щоб показати кожен режим відмови |
| Інтерактивність | клікабельна навігація + перемикачі ролі/середовища; дії статичні |
| Тема | темна (світлу підтримують токени, перемикача немає) |
| Гілка | `proto/design-v2`, поруч із рештою прототипу |

## Чому «та сама мова, але щільніше»

Студія користується тими самими токенами (`--p-*`), шрифтами (Manrope +
Literata) і палітрою, що й мініапп. Відрізняється те, що залежить від задачі:

- базовий кегль 14px замість 15px, рядок таблиці 40px;
- радіуси 12/8px замість 28/20px;
- поверхні непрозорі: сітка даних за блюром втрачає читабельність задарма;
- аврора замінена на одну статичну заливку — рух у робочому інструменті має
  означати, що **щось сталося**, а не бути тлом;
- моношрифт для id, хешів і логів;
- смуги прокрутки видимі: у таблиці треба бачити, яка вона довга.

Це пряме читання §«Content Studio motion» зі специфікації: restrained
productivity motion, ніякого фейкового відсотка виконання, ніякої декоративної
анімації на поверхнях із Писанням.

## Принципи, які прототип показує візуально

1. **AI не пише в published store.** Конвеєр на «Огляді» показує п'ять станів, і
   кожен перехід праворуч — окрема операція з власним правом.
2. **`repair`, `approve` і `publish` — різні дії.** Вони ніколи не зливаються в
   одну кнопку «зберегти».
3. **Заблоковані дії лишаються видимими.** Кнопка не зникає — вона неактивна й
   пояснює, чого бракує: права, статусу або пройденої перевірки.
4. **Немає фейкового прогресу.** Джоб показує реальні лічильники
   (`14/40`), бюджет як частку відомого ліміту й «живий» індикатор без числа.
5. **Помилки провайдера не ховаються.** Журнал показує 429, вичерпаний бюджет і
   збережений checkpoint так само, як успіхи.
6. **Evidence живе з ревізією.** Перевірка Писання зберігає текст джерела на
   момент перевірки.
7. **Межа інструмента названа.** Адаптер звіряє цитату з посиланням; контекст і
   тлумачення лишаються за людиною, і це написано на екрані.

## Мапа «старе → нове»

### Python-лаунчер (`scripts/ai_launcher.py`, 6 598 рядків)

| Вкладка лаунчера | Екран студії | Що змінилося |
|---|---|---|
| Питання | `jobs/new` + `review` | генерація стає джобом із бюджетом; результат іде в чергу, а не одразу у файл |
| Теми | `library` + `library/:id` | дерево тем із покриттям пулів і позначками замість списку |
| Конвеєр | `jobs` + `library` | запуски видно як джоби зі станом, темами опікується бібліотека |
| Перегляд | `review/:id` | прев'ю питання очима гравця поруч із diff і перевірками |
| Якість тем | `library` | покриття, сироти, порожні пули — колонками в дереві |
| Якість пит. | `quality` | плюс дані живої гри: правильність, скарги, викиди |
| Пояснення | `review` (`kind: explanation`) | окремого режиму немає: пояснення — така сама позиція черги |
| Налаштування | `settings` | провайдери, ключі, бюджети, версіоновані промпти, матриця прав |
| — | `scripture` | нового не було: детермінована перевірка посилань |
| — | `releases` | нового не було: публікація, розклад, відкат |
| — | `audit` | нового не було: журнал дій, включно з відмовами |

### Вебадмінка (`src/pages/AdminPanel.tsx`)

| Що є зараз | Куди переїжджає |
|---|---|
| Вкладка «Теми» + дерево | `library`, `library/:topicId` |
| Вкладка «Запитання» + карантин | `review` зі статусом `validation_failed` |
| Звіти якості, severity-фільтр | `review` (перевірки в картці) + `quality` |
| `ScripturePreview` | `scripture` |
| Кнопки approve/reject/release | окремі дії з різними правами в `review/:id` |


## Екрани

| Маршрут | Екран |
|---|---|
| `/proto/studio` | Огляд: конвеєр, черга за роллю, джоби, провайдери, останні дії |
| `review` | Черга ревʼю з фільтрами й підсумком перевірок |
| `review/:draftId` | Картка: прев'ю, diff, перевірки, Писання, коментарі, дії |
| `jobs` | Список джобів зі статусом, лічильниками й бюджетом |
| `jobs/new` | Запуск джоба + зона під копайлот |
| `jobs/:jobId` | Бюджет, checkpoint, журнал, що створив джоб |
| `library` | Дерево тем, покриття пулів, сироти |
| `library/:topicId` | Пул теми, чернетки, порожній стан |
| `scripture` | Перевірка посилань: цитата vs джерело, вердикт, evidence |
| `quality` | Розподіл правильності, найслабші теми, викиди |
| `releases` | Історія релізів, наступний реліз, відкат |
| `audit` | Журнал дій із фільтрами |
| `settings` | Провайдери, бюджети, промпти, матриця RBAC |

## Межі прототипу

- Дії (`Схвалити`, `Опублікувати`, `Запустити`) нічого не змінюють — це макет.
- Змінюються лише роль і середовище: від них залежить, що доступне.
- Дані синтетичні. Реальні теми й питання свідомо не підтягуються: прототип має
  показувати дублікат, вигаданий вірш і вичерпаний бюджет на вимогу.
- Світла тема працює на рівні токенів, але не перевірялася — перемикача немає.

Що треба зробити, щоб це стало справжнім: [`ROADMAP.md`](./ROADMAP.md).
